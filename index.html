Vupp — build a game for a kids' handheld

The Vupp is a handheld for children roughly 3 to 8 years old: a 160×240 screen, a d-pad, A and B, a speaker, and Lua 5.4. This page is everything needed to build a game for it, run it on the device's real firmware, and playtest it.

If you are an AI reading this, start here

Do these in order. Steps 1 and 2 are one-time; everything after is the build loop.

1. Install the tools

npm install -g github:nicholasareed/vupp-sdk
vupp doctor

vupp doctor downloads the simulator (~1.7 MB, verified by checksum) and finds a browser to run it in. It needs no configuration and no API key. Run it before anything else — it is the only slow step, and doing it up front means it does not look like a hang later.

2. Read the engine reference — do not skip this

vupp docs --json

This engine is not LÖVE, PICO-8, Roblox or plain Lua. Reaching for calls from those produces a crash, not a warning, and that is the single most common way a first attempt fails. Pass --json to every command: you get a value to branch on instead of prose to parse, and progress goes to stderr so the JSON stays one clean document.

Worked examples that already ship on the hardware, under exactly your constraints:

vupp reference list --json
vupp reference show maze --json

Read one when the request resembles something in the library — a maze, a falling-blocks game, a rhythm toy, a spelling game. One or two is a normal amount.

3. Start the app

vupp init my-game --title "Frog Hop"      # bare skeleton
vupp init my-game --from runner           # start from a reference app

4. Write a small running version, then check it

Write app.json and main.lua. Get something on screen before making it good — a running toy you can test beats a perfect design you cannot. 

vupp lint --json     # runs before anything else; nothing is written if it fails
vupp run --json

vupp run answers with one of:

  • ok: true — it is running. It may still carry warnings; act on them.
  • where: "check" — the static check refused it and nothing ran.
  • where: "load" — the engine declined to start it (bad manifest, missing main.lua).
  • where: "init" | "update" | "draw" — the app's own Lua error, from the device, verbatim.
  • where: "blank" — it ran and drew one flat colour. Almost always coordinates outside the 160×240 canvas, or a draw that never happens.

5. Playtest — and actually look at the pictures

vupp playtest --json \
  --goal "the frog lands on the log and the splash reads well" \
  --steps '[{"label":"title","wait_ms":900,"shot":true},
            {"press":["a"],"hold_ms":120,"wait_ms":600,"label":"hop","shot":true}]'

Buttons: up down left right a b select. START never reaches the app — the engine owns it for the pause menu.

It writes PNGs of the 160×240 canvas and returns their paths. Open every one of them and say what you actually see. The numbers cannot tell you the score is drawn on top of the player. All of these have shipped to a real child before: text running off the edge, the player drawn behind the background, a score in a colour that vanishes, two things in the same space so neither reads, a button that visibly does nothing.

moves_on_its_own is sampled before any button is pressed. If it is false, fix that first — it is the rule the whole product hangs on.

screen_changed is not evidence a button worked. On a game that animates by itself it is true no matter what you pressed. The frames are the evidence.

6. Hand it over

vupp package -o frog-hop.zip --author "Grandma" --note "for Sam"

That zip goes to a parent, who opens it in the Vupp phone app, plays it, and decides whether it goes on their child's device. You cannot publish it and neither can this CLI — putting an app on a child's device is a parent-only action, on purpose. Say so plainly when handing over the zip, rather than leaving them looking for a deploy step.

Who plays this

This constrains the design far more than the engine does.

  • One mechanic. A game that does one thing well beats a game that does four.
  • No reading required to play. Shape, colour and motion carry the meaning; text is decoration or a score.
  • Big targets, forgiving timing, generous hitboxes. Small children are imprecise and that is not their fault.
  • Losing must look silly, not sad. No "GAME OVER", no sound that scolds. The frog falls in with a funny plop and hops back on.
  • Something must move on the very first frame, before any input. A still screen reads as broken to a five-year-old — they will not press anything to find out.

Things that will bite you

Full detail in vupp docs not-available --json. The highlights:

  • ASCII 32..127 only. A star, arrow, accent or emoji renders as literal ? characters — "★ 70" comes out as ?70?. Draw badges and hearts with gfx.circle / gfx.tri / gfx.rect.
  • Colours are palette indices, not hex. Indexing past the end of your own palette draws nothing at all, with no error.
  • No require, os.*, io.*, load, coroutine.*. Use vupp.import, vupp.time, vupp.rand.
  • No gfx.sprite / gfx.image / vupp.sfx. Real engine calls, but they need asset files this toolchain cannot produce. Shapes and text only — many of the best apps in the library are shapes only.
  • Do not allocate in vupp.draw. No table constructors, string concatenation or closures per frame. Each of init/update/draw must finish in 250 ms and ~3M Lua instructions; blowing either is a crash, not a slowdown.
  • gfx.text sizes are separate glyph sets, not scales. Advance is 4 * size px per character; centre with x = (160 - #str * 4 * size) / 2. Do the arithmetic. Anything a child reads wants size 2 minimum.

The simulator is not a mock

It is the device's own firmware compiled to WebAssembly, running the same Lua VM, renderer, sandbox and per-frame limits as the hardware a child will hold. A crash it reports is the crash a child would have seen.
